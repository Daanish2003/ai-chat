# Research: packaging and publishing a multi-package SDK

Ticket: [#39 Packaging and publishing a multi-package SDK](https://github.com/Daanish2003/ai-chat/issues/39) (child of map #38).
Researched: 2026-10-08. Vocabulary follows `CONTEXT.md` (Host, Conversation, Message). Boundary decisions taken as given from the map: stack-agnostic Hosts, React-only UI plus a headless client, an SDK-owned Postgres schema via internal Drizzle, one web-standard handler, precompiled CSS plus a shadcn registry.

## Question

How should this monorepo build and publish several related packages (server, headless client, React UI) for other repos on other stacks? Which build tool (tsdown, tsup, unbuild, plain tsc)? ESM-only or dual? Changesets for versioning? npm or GitHub Packages? How do we ship precompiled Tailwind v4 CSS so Hosts don't need Tailwind, host a shadcn registry next to the packages, and ship Drizzle migrations that a Host can run?

## Recommendation

| Concern                    | Choice                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Build tool                 | **tsdown** (Rolldown + Oxc), one `tsdown.config.ts` per published package. Do not pick tsup (unmaintained, points to tsdown) or unbuild (its authors are moving to a Rolldown-based successor). Keep `tsc` only for typechecking.                                                                                                                                                                                                         |
| Module format              | **ESM-only.** tsdown's default, and what tsdown's docs recommend for new libraries. Node supports `require(esm)` without a flag since 20.19 / 22.12.                                                                                                                                                                                                                                                                                      |
| Types                      | `.d.ts` from tsdown (auto-on when `exports` has `types`). Turn on `isolatedDeclarations` later for speed; it is not required.                                                                                                                                                                                                                                                                                                             |
| Package shape              | Three **published** packages: server, headless client, React UI. Internal workspace packages (`api`, `db`, `ui`, `chat-core`) stay `private` and are **bundled into** the published ones with tsdown's `deps.alwaysBundle`. The React package is built with `unbundle: true` so per-file `'use client'` directives survive for Next.js App Router Hosts.                                                                                  |
| Package checks             | tsdown's `publint: true` and `attw` (profile `esm-only`) in CI.                                                                                                                                                                                                                                                                                                                                                                           |
| Versioning                 | **Changesets** with the three packages in one **`fixed`** group (they share a wire protocol, so one version number for all three), `access: "public"`, released by `changesets/action` from `main`.                                                                                                                                                                                                                                       |
| Registry                   | **npm, public scope.** GitHub Packages needs a token even to _install_ public packages, which is a bad fit for third-party Hosts. Publish with **trusted publishing (OIDC)** from GitHub Actions instead of an `NPM_TOKEN`. The scope name is still an open question on the map.                                                                                                                                                          |
| CSS, Host without Tailwind | Build `styles.css` with the **Tailwind v4 CLI** (`@tailwindcss/cli`) from an entry that uses `source(none)` + `@source` on the SDK's own components only. Export it as `@<scope>/react/styles.css`. All of it stays inside Tailwind's cascade layers, so any unlayered Host CSS wins over it.                                                                                                                                             |
| CSS, Host with Tailwind v4 | Export a small `theme.css` (the shadcn CSS variables, `@custom-variant dark`, plugins) and tell the Host to add `@source "../node_modules/@<scope>/react/dist"`. The Host's own Tailwind then generates the classes once, with no duplicated utilities or second Preflight.                                                                                                                                                               |
| shadcn registry            | A `registry.json` in the repo, built to static JSON with `shadcn build` (default output `public/r`), served from `apps/web` (the reference Host) under `/r/*.json`. Hosts add it as a namespace in `components.json` and run `shadcn add @<ns>/chat`. Registry items depend on the npm client package for logic and copy only the presentational components.                                                                              |
| Migrations                 | Ship the drizzle-kit migration folders (`<timestamp>_<name>/migration.sql`) as files inside the server package. Expose `chat.migrate()` (and a tiny CLI bin) that calls Drizzle's runtime `migrate()` with a **separate `migrationsSchema`/`migrationsTable`**, so it never collides with a Host that also uses Drizzle. Run it as a release or one-off step, not on every boot, because the migrator takes no advisory lock (see below). |

## Findings

### 1. Build tools

- **tsup is no longer maintained.** Its README opens with: "This project is not actively maintained anymore. Please consider using tsdown instead." ([egoist/tsup](https://github.com/egoist/tsup)). Last npm publish was 8.5.1 on 2025-11-12 (`pnpm view tsup`).
- **tsdown** is "an official project of Rolldown", built on Rolldown (Rust), and lists tsup as prior art with a migration guide ([tsdown guide](https://tsdown.dev/guide/)). Defaults that differ from tsup: ESM format, `clean: true`, dts auto-enabled when `package.json` has `types`, target read from `engines.node` ([migrate from tsup](https://tsdown.dev/guide/migrate-from-tsup)). Latest is **0.23.0 (pre-1.0)**. The migration guide warns that newer versions removed the tsup-compatible options, so breaking changes do happen between minors.
  - `exports: true` "automatically analyze[s] your entry points and output files, and update[s] the `exports` field in your `package.json`". `devExports` keeps source paths for development and writes built paths into `publishConfig` for publishing ([package exports](https://tsdown.dev/options/package-exports)). That fits the current repo, where every `exports` points at `./src/*.ts`.
  - `dependencies` and `peerDependencies` are external by default. `deps.alwaysBundle: ['pkg']` forces a package into the bundle; `noExternal` is deprecated in favour of it ([dependencies](https://tsdown.dev/options/dependencies)).
  - `unbundle: true` makes "output files that closely mirror your source module structure" ([unbundle](https://tsdown.dev/options/unbundle)).
  - `publint` and `attw` options run publint and Are-the-types-wrong during the build, with an `esm-only` profile for attw ([lint](https://tsdown.dev/options/lint)).
  - `copy` copies files (globs) into the output; `workspace` is an **[experimental]** monorepo mode ([UserConfig](https://tsdown.dev/reference/api/Interface.UserConfig)).
  - CSS support exists through `@tsdown/css` but "is still an experimental feature" ([CSS](https://tsdown.dev/options/css)). That is why the recommendation builds CSS with the Tailwind CLI instead.
  - JSX/TSX works with no plugin ([React recipe](https://tsdown.dev/recipes/react-support)).
- **unbuild** is Rollup-based (plus mkdist for file-to-file output). Its README says "We are experimenting with obuild as the next next-gen successor based on rolldown" ([unjs/unbuild](https://github.com/unjs/unbuild)). Last publish 3.6.1 on 2025-08-15; obuild is at 0.4.x.
- **Plain `tsc`** emits one JS file per TS file and `.d.ts`, but it does not bundle the private workspace packages, rewrite `exports`, process CSS, or run publint/attw. We would have to publish `@ai-chat/api`, `db`, `ui` and `chat-core` as well, which turns internals into public API.

### 2. ESM-only vs dual

- tsdown: "CJS is in maintenance-only mode … New libraries are encouraged to publish ESM-only." ([output format](https://tsdown.dev/options/output-format)).
- Node: `require(esm)` is off the flag since v20.19.0 / v22.12.0 / v23.0.0, and stable since v25.4.0. A module graph that uses **top-level `await`** throws `ERR_REQUIRE_ASYNC_MODULE` when `require()`d ([Node modules docs](https://nodejs.org/api/modules.html#loading-ecmascript-modules-using-require)). So: ESM-only, and **no top-level `await` in the published entry points**, so CJS Hosts on modern Node can still `require()` us.

### 3. React UI and Next.js Hosts

- `'use client'` must be at the top of the file, before imports, and only the files a Server Component renders directly need it ([Next.js `use client`](https://nextjs.org/docs/app/api-reference/directives/use-client)). A single-file bundle loses or misplaces per-file directives, so the React package should be built with `unbundle: true`. Several projects report that tsdown in unbundle mode keeps each file's directive (search results only: e.g. [rolldown#7809](https://github.com/rolldown/rolldown/issues/7809) on directives not being preserved when bundling). **Unverified: check the built output for directives in the first build ticket.**

### 4. Versioning: Changesets

- `fixed`: packages "should be version-bumped and published together". `linked`: packages "share" a version but only the changed ones are bumped. `access` defaults to `restricted`. `privatePackages` defaults to not versioning or tagging private packages ([config options](https://github.com/changesets/changesets/blob/main/docs/config-file-options.md)). Latest `@changesets/cli` is 3.0.3.
- pnpm's guide: `pnpm add -Dw @changesets/cli`, `pnpm changeset init`, then `pnpm changeset version` and `pnpm publish -r` ([pnpm + changesets](https://pnpm.io/using-changesets)). `pnpm -r publish` skips versions already on the registry ([pnpm publish](https://pnpm.io/cli/publish)).
- On publish pnpm rewrites `workspace:*` to the exact version, `workspace:^` to `^x.y.z` ([workspaces](https://pnpm.io/workspaces)), and removes `catalog:` in favour of the real range ([catalogs](https://pnpm.io/catalogs)). The repo's catalog dependencies therefore need no special handling.
- `changesets/action` opens a "Version Packages" PR and publishes after it merges. It needs `contents: write`, `pull-requests: write`, `id-token: write` for OIDC, and "Allow GitHub Actions to create and approve pull requests" turned on ([changesets/action](https://github.com/changesets/action)). Input names should be checked against the action's `action.yml` when the workflow is written; the README summary I read named them `publish-script` / `version-script`, which may be a newer rename.

### 5. Registry: npm vs GitHub Packages

- **GitHub Packages**: scoped packages only, and the scope must match the GitHub owner. "You need an access token to publish, install, and delete private, internal, and public packages." Consumers add `@NAMESPACE:registry=https://npm.pkg.github.com` to `.npmrc` ([GitHub Packages npm](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-npm-registry)). Every Host, including CI and Docker builds, would need a GitHub token to install the SDK.
- **npm**: scoped packages are private by default; publish public with `--access public` (or Changesets `access: "public"`) ([scoped public packages](https://docs.npmjs.com/creating-and-publishing-scoped-public-packages)). Trusted publishing needs npm CLI ≥ 11.5.1, Node ≥ 22.14.0, and `id-token: write`. Provenance is then generated automatically for public packages from public repos ([trusted publishers](https://docs.npmjs.com/trusted-publishers)).
- pnpm's publish docs mention provenance from supported CI ([pnpm publish](https://pnpm.io/cli/publish)). That pnpm 11+ does the OIDC exchange itself comes **only from search results** (third-party PRs and [pnpm#16721](https://github.com/pnpm/pnpm/issues/16721)), not from pnpm docs. This repo pins `pnpm@12.6.0`. **Unverified: confirm on the first dry-run release; the fallback is `npm publish` for the publish step only.**
- npm pricing for private packages was not checked. A private-first phase is better done with Changesets snapshot/prerelease versions on the public scope than with paid private packages.

### 6. Precompiled Tailwind v4 CSS

- The CLI: `@tailwindcss/cli -i input.css -o output.css` (plus `--minify`) ([Tailwind CLI](https://tailwindcss.com/docs/installation/tailwind-cli)).
- `@import "tailwindcss" source(none);` turns off automatic detection so only explicit `@source` paths are scanned. Tailwind ignores `node_modules` by default, and an external library built with Tailwind is registered with `@source "../node_modules/@acmecorp/ui-lib"` ([detecting classes](https://tailwindcss.com/docs/detecting-classes-in-source-files)). That supports both CSS paths in the recommendation.
- `@import "tailwindcss"` is `theme.css` in `layer(theme)`, `preflight.css` in `layer(base)`, `utilities.css` in `layer(utilities)`. Leaving out `preflight.css` turns off the global reset ([Preflight](https://tailwindcss.com/docs/preflight)).
- "Styles that are not defined in a layer always override styles declared in named and anonymous layers." ([MDN @layer](https://developer.mozilla.org/en-US/docs/Web/CSS/@layer)). Hosts can therefore override SDK styles with plain CSS.
- `prefix(tw)` prefixes classes (`tw:text-red-500`) and theme variables ([utility classes](https://tailwindcss.com/docs/styling-with-utility-classes)). **Not recommended here:** every class string in `packages/ui` and `packages/chat-react` would need rewriting, and registry consumers would receive prefixed classes they don't want. Collisions without a prefix are mild: the same utility name produces the same rule, and the shadcn variables (`--background`, `--primary`, …) are the intended theming hook.
- Today `packages/ui/src/styles/globals.css` uses `@source "../../../apps/**/*.{ts,tsx}"`, and `apps/web/src/index.css` adds `@source` for `chat-react`. The published build needs its own entry that scans only SDK source.
- **Open trade-off: Preflight.** Shipping it in `styles.css` resets the whole Host page; leaving it out may make components look off in Hosts with no reset. Suggested: `styles.css` without Preflight plus an optional `preflight.css`. Validate this in the example Host (Next.js + Prisma) ticket.

### 7. shadcn registry

- `registry.json` at the root lists items; `shadcn build` writes static JSON, by default to `public/r`, served as `/r/[NAME].json`. Consumers run `shadcn add <url>` or register a namespace in `components.json` (`"@acme": "https://acme.com/r/{name}.json"`) and run `shadcn add @acme/button` ([registry getting started](https://ui.shadcn.com/docs/registry/getting-started)). This repo already consumes `@prompt-kit` the same way (`packages/ui/components.json`).
- Items declare `type` (`registry:ui`, `registry:block`, `registry:lib`, `registry:hook`, …), `files` with optional `target`, npm `dependencies`, `registryDependencies` (built-in names, `@ns/item`, URLs), `cssVars` and `css` ([registry-item.json](https://ui.shadcn.com/docs/registry/registry-item-json)). A `chat` block can therefore depend on `@<scope>/client` from npm and on shadcn's `button`, etc.
- Private registries can send auth headers with `${ENV_VAR}` expansion. There is an open-source registry index that namespaces can join ([namespaces](https://ui.shadcn.com/docs/registry/namespace)).
- The docs say "Imports should always use the `@/registry` path". Our components import `@ai-chat/ui/...`, so the registry items need rewritten imports or a build step. **Size this in the registry ticket.**

### 8. Drizzle migrations inside a published package

- Tables live in their own schema through `pgSchema("…")`; queries are then schema-qualified ([schemas](https://orm.drizzle.team/docs/schemas)). drizzle-kit's `schemaFilter` limits push/pull to listed schemas ([config](https://orm.drizzle.team/docs/drizzle-config-file)). Today `packages/db/drizzle.config.ts` has `schemaFilter: ["public"]`, so moving to an SDK schema means changing this and adding a migration. That is a schema decision for a human (AGENTS.md §6).
- Runtime migration: `migrate(db, config)` from `drizzle-orm/node-postgres/migrator` ([migrations](https://orm.drizzle.team/docs/migrations)). The installed `drizzle-orm@1.0.0-rc.4` types read: `MigrationConfig { migrationsFolder: string; migrationsTable?: string; migrationsSchema?: string }`. It defaults to `drizzle.__drizzle_migrations`, runs `CREATE SCHEMA IF NOT EXISTS`, and reads `<migrationsFolder>/<subdir>/migration.sql` from disk (`node_modules/drizzle-orm/migrator.js`, `pg-core/async/session.js`). drizzle-kit uses the same defaults ([drizzle-kit migrate](https://orm.drizzle.team/docs/drizzle-kit-migrate)).
  - The SQL files have to exist **as files** in the published package (in `files`, copied next to the bundle with tsdown `copy`). The path should come from `new URL("./migrations", import.meta.url)`, which the repo already does in `packages/db/src/testing/test-database.ts`.
  - A Host that also uses Drizzle keeps its own history in `drizzle.__drizzle_migrations`. If the SDK used the same table, the two histories would mix. **Use the SDK's own `migrationsSchema`** (for example the SDK's Postgres schema).
  - In the source I read, `migrate()` runs pending migrations in one transaction, and I found **no advisory lock**. Several processes starting at once could race, so make migration an explicit deploy step (`chat.migrate()` / a CLI bin), or wrap it in `pg_advisory_lock` ourselves.
- `drizzle-kit` stays a devDependency of the SDK repo (to generate migrations). Hosts need only `drizzle-orm` + `pg`, as runtime `dependencies` of the server package.

## Implications for this repo

- `packages/chat-core` and `chat-react` are `private` and export `./src/*.ts`; `api`, `auth`, `db` have no version. The published set would be new or renamed packages (server, client, react), each with a `tsdown.config.ts`. `turbo.json`'s `build` already caches `dist/**`.
- Bundling `@ai-chat/api` and `@ai-chat/db` into the server package means their third-party dependencies (`drizzle-orm`, `pg`, `@orpc/*`, `@tanstack/ai*`, `zod`) must be listed in the **published** package's `dependencies`. Bundling a workspace package does not pull in its dependency list automatically. **Unverified how tsdown reports a missing one; publint/attw won't catch it. A pack-and-install smoke test in the example Host would.**
- `@ai-chat/auth` (Better Auth) must not reach the published server package, because auth comes from the Host.
- New devDependencies (tsdown, `@changesets/cli`, `@tailwindcss/cli`, publint, `@arethetypeswrong/core`) and the npm scope plus trusted-publisher setup are human decisions (AGENTS.md §6).

## Could not verify / caveats

- Nothing here was built or published end to end. The tsdown, Changesets and shadcn facts come from their docs as fetched on 2026-10-08; tsdown is pre-1.0.
- `'use client'` preservation in tsdown unbundle mode and pnpm's native OIDC publishing come from search results and third-party repos, not first-party docs.
- The exact `changesets/action` input names were not checked against `action.yml`.
- npm private-package pricing was not checked.
- Drizzle's lack of a migration lock comes from reading installed `1.0.0-rc.4` source, not from docs; a later release could add one.
