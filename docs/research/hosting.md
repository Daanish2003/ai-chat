# Research: hosting for a long-running Node app

Ticket: [#41 Hosting for a long-running Node app](https://github.com/Daanish2003/ai-chat/issues/41) (child of map [#38](https://github.com/Daanish2003/ai-chat/issues/38)).
Researched: 2026-10-08. All prices were read on 2026-10-08, are in USD unless marked, and exclude VAT.

## Question

Where should `apps/web` run in production? It is TanStack Start built with Nitro's `node-server` preset (`apps/web/vite.config.ts`), packaged by `apps/web/Dockerfile` as one long-running Node process on port 3001. Assistant runs last up to 5 minutes (ADR 0002). It needs managed Postgres with `pg_trgm` (created in `packages/db/src/migrations/20261006134352_conversation_and_message/migration.sql`), Redis for pub/sub, and S3-compatible storage. The candidates are Fly.io, Railway, Render, and a VPS running Docker (Hetzner with Coolify or Kamal). For each one we compared cost at small scale, streaming timeouts, deploy behaviour for in-flight runs, regions, managed Postgres and Redis, preview environments, and deploys from GitHub Actions.

## Recommendation

**Render**: a Docker web service, Render Postgres and Render Key Value, all in one region (Frankfurt or Virginia). The S3 store comes from another provider when we need one. This is a proposal. Infrastructure is a human decision (AGENTS.md §6).

- It is the only candidate whose request limit is far above our 5-minute run: "Render web services allow HTTP responses to take up to 100 minutes" ([source](https://render.com/docs/render-vs-vercel-comparison)). Fly has no documented maximum but has a reported 30 s stall reset. Railway caps requests at 15 min and closes them after 5 min with no data. Kamal's proxy defaults to 30 s.
- Deploys are zero-downtime by default. The old instance keeps serving until the new one is healthy, then gets `SIGTERM`. The shutdown delay can be raised from 30 s to **300 s** ([source](https://render.com/docs/deploys)), which covers one 5-minute run.
- It has truly managed Postgres with `pg_trgm` documented ([source](https://render.com/docs/postgresql-extensions)) and point-in-time recovery (3 days on Hobby, 7 days on Pro). It also has managed Valkey-based Key Value with persistence on paid plans.
- Small-scale cost is about **$36/month**: Starter web $7, Postgres basic-1gb $19, Key Value starter $10, on the $0 Hobby workspace. Full-stack previews need the Pro workspace (+$25/month).
- It fits our CI: auto-deploy "After CI Checks Pass", a deploy hook URL, or `render deploys create` ([source](https://render.com/docs/deploys)).
- Render has no object storage product (we found none; not verified exhaustively). The map makes Postgres the default blob store, so S3 can wait. When we need it, pick a provider separately.

**Runner-up: Railway**, if cost matters more than a hands-off database. It costs less, has S3-compatible buckets built in, and its 15-minute streaming limit is enough. Its Postgres, though, is a template you partly manage yourself (backups are opt-in, high availability needs a conversion), and draining defaults to 0 s.

**Whatever host we pick, the app has to change first** (see [App-side work](#app-side-work-needed-on-any-host)). Today `apps/web` has no `SIGTERM` handling, and its boot sweep marks every `streaming` row as `error`. So every zero-downtime deploy on any of these hosts would cut off or wrongly fail in-flight runs.

## Findings

### Fly.io

- **Pricing** ([pricing](https://docs.fly.io/about/pricing)): shared-cpu-1x costs $2.19 (256 MB), $3.69 (512 MB), $6.70 (1 GB) or $13.39 (2 GB) per month in the cheapest regions. Egress is $0.02/GB in North America and Europe. A dedicated IPv4 is $2/month, and shared IPv4 is free. Volumes are $0.15/GB/month.
- **Managed Postgres** ([MPG](https://docs.fly.io/mpg)): Basic (shared-2x, 1 GB) costs $38/month and Starter (2 GB) $72/month. Storage is $0.28/GB/month. Automatic failover and backups come with every plan, and Postgres 16 and 17 are supported. `pg_trgm` is listed as supported and is toggled per database ([extensions](https://docs.fly.io/mpg/extensions)). Fly lists version upgrades and alerting as "under development".
- **Redis**: Upstash for Redis on Fly ([docs](https://docs.fly.io/upstash/redis)) costs $0.20 per 100k requests pay-as-you-go, or fixed plans from $10/month (250 MB). The primary region can't be changed after creation. The page doesn't say whether pub/sub is supported (**unverified**). A pub/sub subscriber also costs requests, so check the bill.
- **Timeouts**: `fly.toml` accepts `[http_service.http_options] idle_timeout` in seconds ([configuration](https://docs.fly.io/reference/configuration)). The docs we read state no maximum request duration. A community report from 2026-10-06 says Fly Proxy resets an HTTP stream after about 30 s _when the client stops reading_, whatever `idle_timeout` is set to ([thread](https://community.fly.io/t/fly-proxy-resets-a-stalled-http-stream-after-30s-on-edge-and-flycast-hops-http-options-idle-timeout-has-no-effect/28755), no staff reply). That concerns a stalled reader, not a quiet server, so it shouldn't touch token streams. It is **unverified**.
- **Deploys** ([configuration](https://docs.fly.io/reference/configuration)): `rolling` (the default) replaces Machines one by one. With a single Machine that means downtime. `bluegreen` boots new Machines next to the old ones, moves traffic once health checks pass, then destroys the old ones. `kill_timeout` defaults to 5 s, and the maximum is "300 seconds (5 minutes)". The default `kill_signal` is `SIGINT`, not `SIGTERM`.
- **CI** ([GitHub Actions](https://docs.fly.io/launch/continuous-deployment-with-github-actions)): `superfly/flyctl-actions/setup-flyctl` with a deploy token (`flyctl tokens create deploy`), then `flyctl deploy --remote-only`. Review apps exist as a blueprint you wire up yourself.

### Railway

- **Pricing** ([plans](https://docs.railway.com/reference/pricing/plans)): Free costs $0, Hobby $5/month (includes $5 of usage) and Pro $20/month (includes $20). Resources cost $10/GB RAM/month and $20/vCPU/month. Egress is $0.05/GB and volumes $0.15/GB/month. Hobby allows up to 6 replicas. Billing is by usage, so the $15–25 total is an **estimate** that depends on real RAM and CPU use.
- **Timeouts** ([specs and limits](https://docs.railway.com/networking/public-networking/specs-and-limits)): "HTTP requests can run for up to 15 minutes if data keeps transferring (for example, keep-alive heartbeats), and are otherwise closed after 5 minutes with no data transferred." Request bodies must finish uploading within 5 minutes. WebSockets are exempt. A 5-minute run that keeps sending tokens or heartbeats fits.
- **Deploys** ([teardown](https://docs.railway.com/deployments/deployment-teardown), [config as code](https://docs.railway.com/reference/config-as-code)): once the new deploy is active, the old one gets `SIGTERM`, then `SIGKILL` after `RAILWAY_DEPLOYMENT_DRAINING_SECONDS`. `RAILWAY_DEPLOYMENT_OVERLAP_SECONDS` keeps the old deploy serving for a while. **Both default to 0** (according to Railway's docs as summarised by search; the pages we fetched don't state the defaults). The docs give no maximum.
- **Postgres** ([PostgreSQL](https://docs.railway.com/databases/postgresql)): it is built on "the official Postgres image from Docker Hub" (Railway's SSL variant). Backups have to be set up ("Automate regular backups"). High availability (Patroni) means converting an existing service. Changing the template "makes the database yours to manage". Railway says "we do not plan to add extensions" to the templates. `pg_trgm` is a contrib module that ships in the official image, which is how our `docker-compose.yml` gets it, so `CREATE EXTENSION pg_trgm` should work. We did **not verify this on Railway**.
- **Redis**: a template (container). There is no separately managed offering.
- **Object storage** ([buckets](https://docs.railway.com/storage-buckets)): S3-compatible buckets cost $0.015/GB-month, with free egress and API operations.
- **Regions** ([regions](https://docs.railway.com/deployments/regions)): US West (California), US East (Virginia), EU West (Amsterdam), Southeast Asia (Singapore).
- **CI and previews**: `RAILWAY_TOKEN=<project token> railway up` ([CLI deploying](https://docs.railway.com/cli/deploying)). There is also a documented GitHub Actions workflow that creates a Railway environment per PR and deletes it on close ([guide](https://docs.railway.com/guides/github-actions-pr-environment)).

### Render

- **Pricing** ([pricing](https://render.com/pricing)): workspaces are Hobby $0 + compute, or Pro $25/month + compute. Web services cost Starter $7 (512 MB), Standard $25 (2 GB) or $85 (4 GB). Postgres costs basic-256mb $6, basic-1gb $19 or basic-4gb $55 (approximately; read from the compute table), with storage at $0.30/GB. Key Value costs Starter $10 (256 MB) or $20 (1 GB). Bandwidth: 5 GB included on Hobby and 25 GB on Pro, then $0.15/GB. Build minutes: 500/month on Hobby.
- **Timeouts**: "Render web services allow HTTP responses to take up to 100 minutes" ([source](https://render.com/docs/render-vs-vercel-comparison)).
- **Deploys** ([deploys](https://render.com/docs/deploys)): if the build fails, the old instance keeps running. The old instance serves until the new one is healthy, then gets `SIGTERM`. The shutdown delay is 30 s by default and up to 300 s through the API or `render.yaml`, then `SIGKILL`. The docs name "responding to remaining in-flight HTTP requests" as what that window is for.
- **Postgres** ([extensions](https://render.com/docs/postgresql-extensions)): `pg_trgm` is supported. It is enabled with `CREATE EXTENSION pg_trgm;` on PG 13+. The point-in-time recovery window is 3 days on Hobby and 7 days on Pro, according to the pricing page.
- **Key Value** ([docs](https://render.com/docs/key-value)): "compatible with virtually all clients that interact with Redis". New instances run Valkey 8. Paid instances persist data (journal + snapshot by default), and free ones don't. Valkey has pub/sub, but this page doesn't mention it (**unverified for Render**).
- **Previews** ([preview environments](https://render.com/docs/preview-environments)): full-stack preview environments need Pro or higher. They copy datastores _without_ data and are billed per second like other services. Single-service previews work on Hobby.
- **Regions** ([regions](https://render.com/docs/regions)): Oregon, Ohio, Virginia, Frankfurt, Singapore. A service's region can't be changed later.
- **CI**: auto-deploy "on Commit" or "After CI Checks Pass", a deploy hook URL (GET or POST), the `render deploys create` CLI, or the API with a `commitId` ([deploys](https://render.com/docs/deploys)).

### Hetzner with Coolify or Kamal

- **Prices from 2026-06-15** ([price adjustment](https://docs.hetzner.com/general/infrastructure-and-availability/price-adjustment/)), all excluding IPv4 and VAT. In Germany and Finland: CX23 (2 vCPU / 4 GB / 40 GB) was €3.99 and is now €5.49 ($6.49). CAX11 (Arm) is €5.99 ($6.99). CPX22 is €19.49. In the USA, CPX11 is €17.49 ($20.49). The cheap lines are effectively EU-only.
- **Availability**: Hetzner's [cost-optimized page](https://www.hetzner.com/cloud/cost-optimized/) shows every CX model as "currently unavailable" as of 2026-10-08. CAX (Arm) would need an arm64 image. `node:24-slim` is multi-arch, but our native dependencies are unchecked.
- **Object Storage** ([page](https://www.hetzner.com/storage/object-storage/)): S3-compatible, in FSN1, HEL1 and NBG1. The base price includes 1 TB stored and 1 TB egress, but the euro amount didn't render on the page (**unverified**).
- **Kamal** ([proxy](https://kamal-deploy.org/docs/configuration/proxy/), [config](https://kamal-deploy.org/docs/configuration/overview/), [kamal-proxy](https://github.com/basecamp/kamal-proxy)): `response_timeout` defaults to 30 s and would have to rise above 300 s. `drain_timeout` defaults to 30 s. kamal-proxy "waits for traffic to drain from the old instance". Let's Encrypt works on a single server. Request and response buffering is configurable: check that it doesn't buffer SSE (**unverified**). Postgres, Redis and backups are yours to run (Kamal "accessories").
- **Coolify** ([rolling updates](https://coolify.io/docs/knowledge-base/rolling-updates)): rolling updates start the new container, wait for its health check, then stop the old one. This works for Dockerfile and image apps only. "Docker Compose applications cannot use rolling updates at all", and publishing a host port also blocks them. So our `docker-compose.yml` can't be deployed as-is with zero downtime: the web app would have to be a Dockerfile app, with Postgres and Redis as separate Coolify resources. Deploys from CI use an authenticated deploy webhook plus an API token ([GitHub Actions](https://coolify.io/docs/applications/sources/github/actions)). Coolify also has preview deployments. We did not check Traefik's streaming timeouts or Coolify's stop grace period (**unverified**).

## App-side work needed on any host

These come from the repo, not from the hosts. Every host above stops the old process during a deploy, so they decide whether a deploy cuts off a run.

1. **Handle `SIGTERM` (and `SIGINT` on Fly).** Nothing in `apps/web` or `packages` listens for it (we grepped for `SIGTERM`). Node then exits immediately, and every in-flight run dies whatever the host's drain window is. On a signal, stop taking new runs, wait for active runs to finish (at most the 5-minute limit), then exit.
2. **Make the boot sweep safe while two versions overlap.** ADR 0002 says "on boot every `streaming` row is set to `error`". In a zero-downtime deploy (Render, Fly `bluegreen`, Railway overlap, Kamal, Coolify), the new instance boots while the old one is still streaming. The sweep would then mark live runs as interrupted. It needs an owner or heartbeat column, or a rule like "`streaming` and not updated for more than N seconds". That is a schema change, so a human decides it.
3. **Keep the run limit at or under the drain window.** Fly and Render both cap the shutdown window at 300 s, exactly the run limit. Set the drain to the maximum and treat any run still going at `SIGKILL` as interrupted.
4. **Send SSE heartbeats** during quiet stretches (tool calls, slow first token). Railway closes requests after 5 min with no data, and proxies in general are friendlier to streams that keep sending.
5. **Build secrets.** The `Dockerfile` mounts `apps/web/.env` as a BuildKit secret because Varlock validates env at build time. The simplest portable path: build the image in GitHub Actions (secrets available there), push it to a registry, then point the host at the image. All four can run a prebuilt image. We did not check each host's flag or setting for this (**unverified**). Also, `ci.yml` only runs on `pull_request`, so a deploy needs a `push` to `main` trigger or the host's "after CI checks pass" setting.
