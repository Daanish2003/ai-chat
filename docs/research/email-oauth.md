# Transactional email and OAuth with Better Auth

Research for [#42](https://github.com/Daanish2003/ai-chat/issues/42) (child of map [#38](https://github.com/Daanish2003/ai-chat/issues/38)). Researched 2026-10-08 against the installed **better-auth 1.7.7** (`pnpm-lock.yaml`, `packages/auth/package.json`), whose docs line is v1.7 (the current "latest" per [better-auth.com/llms.txt](https://better-auth.com/llms.txt)). Prices were read on 2026-10-08.

## Question

For real users, `apps/web` needs password reset, email verification, change email and password, account deletion and OAuth sign-in. What does Better Auth 1.7.7 support for each, which transactional email provider fits (Resend, Postmark, AWS SES, SMTP) for cost, deliverability and local dev, and which OAuth providers are worth starting with?

## Recommendation

1. **Better Auth 1.7.7 covers every flow in core config. No plugin is needed.** Each flow is a config block plus an email callback (`sendVerificationEmail`, `sendResetPassword`, `sendChangeEmailConfirmation`, `sendDeleteAccountVerification`). The existing `verification` table in `packages/db/src/schema/auth.ts` holds the tokens. The change belongs in `createAuth` in `packages/auth/src/index.ts`, which today only sets `emailAndPassword: { enabled: true }`.
2. **Send all mail through one SMTP sender (Nodemailer), with the provider chosen by env vars.** Resend, Postmark and SES all offer SMTP, so the code doesn't depend on which provider you pick and you can switch later by changing env. In local dev the same sender points at **Mailpit** (`localhost:1025`, UI on `:8025`), and Mailpit's REST API lets e2e tests read the links. In unit tests, use a fake that records messages in memory. Nodemailer is a **new dependency**, so a human has to approve it (AGENTS.md §6).
3. **Provider: start on Resend's free tier.** It gives 3,000 emails a month (but only 100 a day), and Better Auth's own docs list it first. Move to Resend Pro ($20 a month for 50k) when the 100-a-day cap starts to bite. **Postmark** is the choice if deliverability matters more than price ($15 a month for 10k, but the free tier is only 100 a month, so it is not a free start). **SES** is the cheapest at volume ($0.10 per 1k) but starts in a sandbox and needs AWS IAM work. Plain SMTP from your own server isn't worth running.
4. **OAuth: start with GitHub and Google.** GitHub is the quickest to set up (an OAuth app with no review, up to 10 callback URLs). Google reaches the most users. With only `openid email profile` scopes it needs **no app verification**, but it must be switched from _Testing_ (capped at 100 test users, with grants that expire after 7 days) to _In production_. Use separate OAuth clients for dev and prod.
5. **Settings to turn on with it:** `requireEmailVerification: true` (it also enables Better Auth's protection against people probing which emails have accounts), `revokeSessionsOnPasswordReset: true`, a confirmation email to the current address on change-email, and `deleteUser.afterDelete` calling the SDK's `chat.deleteUser(id)` (map #38, "Auth comes from the Host"). Better Auth's rate limits on the email endpoints are already on in production (3 per 60 s). They are kept **in memory**, though, so once there are several processes they need `rateLimit.storage` set to `"database"` or `"secondary-storage"`. That ties into the Redis/pub-sub ticket.

Other details that matter:

- **Don't `await` the send inside the callback.** The docs warn that it opens a timing attack, so use `void sendEmail(…)` [BA1]. On a long-running Node process (map #38) the promise still completes, but it must `.catch` and log, because otherwise a send failure becomes an unhandled rejection. `advanced.backgroundTasks.handler` exists for serverless `waitUntil` and isn't needed yet.
- **Probing which emails have accounts:** when `requireEmailVerification: true` (or `autoSignIn: false`), sign-up returns the same 200 whether the email exists or not, and the optional `onExistingUserSignUp` can email the real owner. With the default config, sign-up returns **422** for an existing email [BA2].
- **Social sign-in is not gated by `emailAndPassword.requireEmailVerification`.** Each provider has its own `requireEmailVerification` setting (default false) [BA5]. Google and GitHub verify emails themselves, so leave it off.
- **Rate limits (verified in `better-auth/dist/api/rate-limiter/index.mjs`):** the global limit is 100 requests per 10 s. `/sign-in*`, `/sign-up*`, `/change-password` and `/change-email` allow **3 per 10 s**. `/request-password-reset` and `/send-verification-email` allow **3 per 60 s**. Rate limiting is off in development, is stored in memory by default, and doesn't apply to server-side `auth.api` calls [BA7].
- **Schema:** no new table is needed for these flows, because tokens go in the existing `verification` table. _Not verified:_ whether 1.7.7 wants any new column. Run `pnpm dlx auth@latest generate` and compare the output with `packages/db/src/schema/auth.ts` before shipping. A schema change would be a human decision.

**Rough monthly cost:** at about 1,000 auth emails a month, Resend and SES cost $0 and Postmark costs $15. At about 30,000 a month, SES costs about $3, Resend Pro $20, and Postmark Basic about $15 + 20 × $1.80 = **$51**. For an auth-only mail volume, Resend's free tier covers the launch. The binding limit is **100 a day**, which a busy sign-up day or a reset storm could exceed.

**Deliverability is mostly about DNS, not the vendor.** Gmail requires SPF _or_ DKIM from every sender, and SPF _and_ DKIM _and_ DMARC (policy `none` is enough) from senders of 5,000+ a day, plus a spam rate below 0.3% [G1]. Whichever provider you pick, set up all three on a sending subdomain such as `mail.<domain>`. One-click unsubscribe only applies to marketing mail, so auth email doesn't need it [G1].

**Not verified:** none of the providers' deliverability claims (inbox placement rates) were checked. Postmark's transactional-only focus and separate streams are its documented advantage. No independent placement data was used.

### Local dev and tests

- **Mailpit** is an SMTP server that catches mail and shows it in a web UI, and it has a REST API for integration tests [M1]. Run it with `docker run -p 8025:8025 -p 1025:1025 axllent/mailpit`: SMTP on **1025**, UI on **8025** [M2]. It fits as a `mailpit` service in `docker-compose.yml`, next to Postgres. The Playwright e2e tests can fetch the newest message through its API and follow the verify or reset link.
- **Console sender:** log `to`, `subject` and the `url`. It's handy when Docker isn't running, but Mailpit catches the real rendered message, so prefer Mailpit in dev and an in-memory fake in unit tests.
- **Sketch of the sender seam:** `sendEmail({ to, subject, text, html })`, built from env as Nodemailer `createTransport({ host, port, secure, auth })` [N1]. Possible env vars for `apps/web/.env.schema`: `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `EMAIL_FROM`. In dev they point at Mailpit without auth, and in prod at the provider. The Resend or Postmark HTTP SDKs offer webhooks and tags, but they'd be another dependency and would lock in a vendor. SMTP is enough for auth mail.

## OAuth providers

### GitHub

- Create an **OAuth app** at <https://github.com/settings/developers>. An OAuth app is simpler than a GitHub App: there's nothing extra to configure. A GitHub App needs _Account permissions → Email addresses: Read-only_, or sign-in fails with `email_not_found` [BA6].
- Callback URL: `<BETTER_AUTH_URL>/api/auth/callback/github` (in local docker-compose `BETTER_AUTH_URL` is `http://localhost:3001`). An OAuth app accepts **up to 10 callback URLs** [GH1], but separate dev and prod apps keep the secrets apart.
- Better Auth requests `user:email` by default. If the user's email is private, `/user` returns `null`. The installed 1.7.7 provider (`@better-auth/core/dist/social-providers/github.mjs`) then calls `/user/emails` itself, takes the primary address, and sets `emailVerified` from GitHub's `verified` flag. So `email_not_found` mainly happens with a GitHub App that lacks the email permission [BA6]. GitHub issues no refresh token, and its access tokens last until revoked, or until unused for a year [BA6]. GitHub supports PKCE with S256 [GH2].
- Env: `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`.

### Google

- In Google Cloud Console, go to **APIs & Services → Credentials → Create OAuth client ID → Web application**, and add the redirect URIs `http://localhost:3001/api/auth/callback/google` and `https://<domain>/api/auth/callback/google`. `baseURL` / `BETTER_AUTH_URL` must be correct, or Google returns `redirect_uri_mismatch` [BA4].
- Configure the consent screen. Requesting only the non-sensitive `openid email profile` scopes means **app verification is not required**. Showing the app name and logo needs the lighter **brand verification** [GO1].
- **Publishing status:** while it's _Testing_, only 100 listed test users can sign in and their grants expire after 7 days. Switch it to _In production_ before launch [GO2].
- Optional: `prompt: "select_account"` makes Google always show the account picker [BA4]. A refresh token isn't needed for sign-in only.
- Env: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`.

### Account linking

Linking is on by default, and it links automatically only when the provider reports the email as verified [BA3]. Google and GitHub both report a trustworthy verified flag [BA5], so a user who signed up with email and password and later uses "Sign in with Google" on the same address ends up with one user. Don't add them to `trustedProviders`, since that forces linking even without verification [BA3]. Consider `disableImplicitLinking: true` if linking should only happen from a settings page.

## Open items for a human (AGENTS.md §6)

- New dependency: `nodemailer` (and `@types/nodemailer`).
- Infrastructure: a sending domain with DNS records (SPF, DKIM, DMARC), a Resend account, Google Cloud and GitHub OAuth apps, and a Mailpit service in `docker-compose.yml`.
- Auth: turning on `requireEmailVerification` means existing v1 users (`emailVerified = false`) can't sign in until they verify. They'll get a fresh email on sign-in if `sendOnSignIn` is on. Decide whether to backfill them as verified or make them verify.
- Possible schema change after running `auth generate` (see the Schema note above).
